Welcome to the AWS AI League
Compete head-to-head with other builders to customize AI models in this hands-on workshop. You'll tackle real-world challenges as you experiment with model customization and fine-tune models to improve accuracy, clarity, and relevance. Learn just how accessible and cost-effective AI customization can be as you customize Amazon Nova Micro, deploy it to Amazon Bedrock, and compete on the leaderboard.

Whether you're chasing the championship or sharpening your AI expertise, this session delivers practical techniques you can apply immediately.

What You'll Learn
In this workshop, you will:

Fine-tune Amazon Nova Micro using Amazon SageMaker AI with training datasets
Deploy your customized model to Amazon Bedrock for serverless inference
Register and submit your model to the AI League leaderboard
Iterate and improve your model using data curation and hyperparameter tuning techniques
Apply practical AI customization skills to real-world challenges
Workshop Modules
Model Training - Fine-tune Amazon Nova Micro with sample datasets using SageMaker AI (~20 minutes)
Model Deployment - Deploy your trained model to Amazon Bedrock (~15 minutes)
Registration & Submission - Register your model and submit to the leaderboard
Model Improvement - Learn techniques to enhance accuracy and climb the rankings
Estimated Duration: 2-3 hours

Target Audience
This workshop is designed for:

Developers interested in AI model customization
ML practitioners exploring foundation model fine-tuning
Anyone curious about competing in AI challenges
No prior machine learning experience required - we'll guide you through each step.

Prerequisites
Basic familiarity with AWS Console navigation
Understanding of JSON file formats for training data
Access to an AWS-hosted AI League event (Workshop Studio provisioned account required)

Click the Customize model dropdown in the upper right corner.

Customize with UI option in dropdown menu

Step 5 - Configure customization settings
You'll see the Model customization screen. Enter a Custom model name using the format model-[XX] (e.g., model-01, model-02). Then under Model and technique:

Verify Base model shows Nova Micro
Leave Customization technique on Supervised Fine-Tuning
Leave Training type on LoRA
Leave Sequence length on 8K
Why LoRA and 8K? LoRA (Low-Rank Adaptation) trains a small set of adapter weights instead of every parameter in the model, which is cheaper than full-rank training and less likely to overfit on a dataset this small. 8K caps each training example at 8,192 tokens, comfortably more than a short prompt-and-response pair needs. Context length also influences which instance types your job runs on, so 8K keeps you on the cost-optimized path. Raise it only if your training examples are genuinely longer than that.
Job names must be unique or the job will fail. Increment the model number (XX) for each new training job.
Model customization screen with the Custom model name field and Supervised Fine-Tuning option highlighted

Understanding the dataset format

{
  "schemaVersion": "bedrock-conversation-2024",
  "system": [
    {
      "text": "You are a helpful assistant that answers questions accurately and concisely."
    }
  ],
  "messages": [
    {
      "role": "user",
      "content": [
        {
          "text": "When did Virgin Australia start operating?\n\nVirgin Australia, the trading name of Virgin Australia Airlines Pty Ltd, is an Australian-based airline. It is the largest airline by fleet size to use the Virgin brand. It commenced services on 31 August 2000 as Virgin Blue, with two aircraft on a single route. It suddenly found itself as a major airline in Australia's domestic market after the collapse of Ansett Australia in September 2001. The airline has since grown to directly serve 32 cities in Australia, from hubs in Brisbane, Melbourne and Sydney."
        }
      ]
    },
    {
      "role": "assistant",
      "content": [
        {
          "text": "Virgin Australia commenced services on 31 August 2000 as Virgin Blue, with two aircraft on a single route."
        }
      ]
    }
  ]
}

Reading that record field by field:

schemaVersion labels the format. Leave it as bedrock-conversation-2024.
system is optional, and it is where persistent instructions belong: output format, persona, domain context. Keep it short, or leave it out. The leaderboard sends only the question when it evaluates your model, with no system prompt, so anything you rely on here will be missing at scoring time. Behaviour you want scored has to be learned from the user turn alone.
messages is the training pair. Only user and assistant roles are supported, the first turn must be user, and the last must be assistant. Both turns nest their text inside a content array, which is why the structure looks deeper than it first appears.
\n\n in the user turn separates the question from the passage it depends on. There is no separate field for supporting text, so anything the answer relies on has to live in the user turn.
Some strings are reserved and will fail your training job if they appear anywhere in a user or system prompt: User:, Bot:, Assistant:, System:, <image>, <video>, and [EOS]. If your data needs them, substitute wording that means the same thing.
Nova Micro accepts up to 20,000 records and needs at least 100, since smaller datasets fail during training. AWS recommends at least 200 samples for each task you want the model to learn. Grow it from there once you can see what is working, bearing in mind that a larger dataset means a longer training run. Full requirements are in Preparing data for fine-tuning .

When you build your own dataset in Module 4, reuse this structure exactly. Those three fields are all there is, so the only thing to get right is the message pairs.

The sample dataset is derived from the databricks-dolly-15k  dataset, Copyright (2023) Databricks, Inc., used under the CC BY-SA 3.0  licence. It has been modified: a subset of records was selected and reformatted into the bedrock-conversation-2024 structure Nova requires. Portions derive from Wikipedia, Copyright Wikipedia editors and contributors, also under CC BY-SA 3.0. The modified dataset remains under CC BY-SA 3.0.

Step 12 - Configure hyperparameters and submit
Expand the Hyperparameters section. The values are already pre-filled with sensible defaults:

Batch size: 64 - total samples per step
Number of epochs: 2 - how many passes the model makes over your data (the form accepts 1 to 100, but AWS recommends 5 or fewer)
Learning rate: 0.00001 - how fast the model updates from data
Expanding Advanced hyperparameters reveals Alpha value, Learning rate ratio, Maximum Context Length, Warmup steps, and Minimum learning rate.

Leave everything at its default for your first training job. The goal right now is simply to get a model onto the leaderboard. Tuning these values is how you climb it, and Module 4: Improving your model explains what each one does and how to experiment with them.
Click the Submit button at the bottom to start your training job.

Module 2: Deploy Model to Amazon Bedrock
Now that your training job is complete, you'll deploy the fine-tuned model to Amazon Bedrock for inference. Amazon Bedrock Custom Model Import allows you to bring your own fine-tuned models and deploy them as fully managed endpoints. This provides on-demand inference with automatic scaling, built-in security, and seamless integration with other AWS services, without the need to manage infrastructure.

Benefits of deploying to Amazon Bedrock:

Serverless inference: No infrastructure to manage or scale
Pay-per-use pricing: Only pay for the inference requests you make
Enterprise security: Built-in encryption and access controls
Easy integration: Use the same Bedrock API for all your models
Step 1 - Open the Actions menu
After clicking "View custom model" in Module 1, you'll land on your custom model page. Click the Actions dropdown in the upper right corner.

Custom model page with Actions dropdown in the upper right

Step 2 - Select Deploy with Bedrock
From the dropdown menu, select Deploy with Bedrock.

Choose Deploy with Bedrock, not Deploy with SageMaker. The leaderboard evaluates a Bedrock deployment ARN, and a SageMaker endpoint will be rejected at submission.
Actions menu expanded with Deploy with Bedrock highlighted

In the Deploy to Amazon Bedrock dialog:

Leave On-Demand selected as the deployment option
Enter a Deployment name using the format: deployment-[XX] (e.g., deployment-01, deployment-02)

Click Deploy
Deployment names must be unique. Valid characters are A-Z, 0-9, underscore and hyphen.
Deploy to Amazon Bedrock dialog showing On-Demand selected, deployment name, and IAM role

Step 6 - Copy the Deployment ARN and test your model
On the deployment details page, verify the status shows In service, then copy the Deployment ARN highlighted below. You'll need it to register your model in Module 3.

Copy the Deployment ARN, not the Model ARN. Both appear side by side on this page and they look almost identical. The Deployment ARN contains custom-model-deployment/, while the Model ARN contains custom-model/imported/. Submitting the Model ARN will cause your leaderboard evaluation to fail.
Testing here is optional but recommended. A quick prompt confirms your model responds the way you expect before it is scored.
Below the summary, the Playground section lets you test your fine-tuned model before you submit it. Enter a prompt and click Run. You can also adjust:

Length - Maximum output tokens (default 512)
Randomness and diversity - Temperature, Top P, Top K

Creating Better Training Data
The foundation of any successful fine-tuning project is high-quality training data. Think of your training data as the textbook your model studies from. Just as a student learns better from a well-written textbook with diverse examples, your model performs better with carefully curated, varied training data.

Build for the challenge you are actually scored on. Read your event's challenge description before you write a single example. Your model is judged against a fixed set of evaluation questions, and a dataset about a different subject will score near zero no matter how clean it is.
Note: This guide uses Vegas tourism as its running example to demonstrate curation technique. The principles of quality, diversity and consistency apply to any subject, whether you are building a customer service bot, a technical documentation assistant, or a domain expert. Copy the method, not the topic.
Start by finding out how your model actually fails
If you already have a deployed model, do this before you write a single new example. It is free, it takes ten minutes, and it does not consume a training run or a deployment slot.

Open your deployment in the Bedrock Playground (Module 2 Step 6) and ask it the kind of questions your challenge is about. Then look for the specific way it is falling short:

Does it answer the wrong subject, or drift off topic?
Is the format wrong, too long, too short, or inconsistent between similar questions?
Is the tone off, generic, or robotic?
What does it do with a question it cannot answer? Does it invent something?
Whatever you see there is what your dataset needs to demonstrate. Rewriting data without doing this is guessing, and each guess costs you roughly an hour once you retrain, redeploy and wait for a score.

Understanding Supervised Fine-Tuning Data
Supervised fine-tuning (SFT) teaches your model to respond in specific ways by learning from example conversations. Each training example consists of an instruction or input (what the user asks) and a response or output (how the model should answer). Your data should teach the model to answer the way your challenge rewards: the right subject matter, a consistent voice, and a useful level of detail.

One thing to understand before you start. AWS is explicit that supervised fine-tuning teaches behaviour, not facts:

SFT teaches the model new behaviors, response formats, and reasoning patterns. It does not teach the model new factual knowledge.

So a dataset written to make the model memorise trivia will disappoint you. What moves a score is consistent structure, appropriate tone, sensible length, and sane handling of questions the model cannot answer. Write examples that demonstrate how to answer.

The Five Pillars of Quality Data
Creating effective training data requires attention to five key principles:

The Five Pillars of Quality Training Data
1. Clarity - Instructions should be unambiguous and easy to understand

✅ Good: "What are the best pizza places on the Strip?"
❌ Vague: "Tell me about food"
2. Relevance - Every example aligns with your use case (Las Vegas tourism)

Stay focused on practical information visitors actually need
Avoid generic content that doesn't serve your theme
3. Consistency - Maintain uniform formatting throughout

Use consistent JSON structure
Keep similar tone and style across all examples
4. Accuracy - Verify all factual information

Check locations, hours, prices, and recommendations
Outdated or wrong information teaches your model to be unreliable
5. Completeness - Responses should be thorough but concise

Aim for 2-4 sentences for most responses
Provide enough detail to be helpful without overwhelming
Building Dataset Diversity
Training a model with limited data diversity is like training for a triathlon by only practicing swimming. You need to practice swimming, biking, AND running to succeed in the actual event. Your dataset needs variety across multiple dimensions to prepare your model for real-world questions.

Dataset Diversity Dimensions
Question Types:

Factual queries: "What are the operating hours for the Bellagio Conservatory & Botanical Gardens?"
Opinion/Recommendations: "Which Vegas buffet offers the best value for money?"
Comparisons: "Should I stay at the Venetian or Bellagio for a luxury experience?"
Planning: "How should I plan a 4-day Vegas trip with both gambling and non-gambling activities?"
Practical: "What's the most efficient way to get from Harry Reid International Airport to the Strip?"
Complexity Levels:

Simple: Single-fact questions
Moderate: Questions requiring context
Complex: Multi-part questions or scenarios
Response Lengths:

Short: 1-2 sentences for quick facts
Medium: 2-3 sentences for recommendations
Detailed: 3-4 sentences for complex topics
Topic Coverage:

Attractions (museums, landmarks, parks)
Food & dining (restaurants, cuisines, food tours)
Transportation (Monorail, rideshare, the Deuce, walking)
Culture & entertainment (resident headliners, Cirque shows, music, art)
History & architecture
Neighborhoods & districts
Practical tips (safety, etiquette, money)
Seasonal events & activities
User Personas:

First-time visitors
Families with children
Business travelers
Budget-conscious tourists
Luxury travelers
Local experiences seekers
Target: Aim for 10-15 examples per major category, mixing question formats and varying response styles.

Common Diversity Pitfalls
Data Curation Workflow
Follow this systematic six-step approach to create high-quality training data. First, generate your initial dataset using focused, category-specific prompts, or write examples by hand, starting with about 100 examples. Your account already has a Code Editor space with Amazon Q built in for exactly this, covered in Using a GenAI tool to build your dataset below. Second, review each example carefully for accuracy, clarity, and relevance, removing or fixing problematic examples and ensuring proper JSON formatting. Third, enhance diversity by identifying gaps in coverage and creating additional examples to fill them, balancing your dataset across all dimensions while adding personality and Vegas character to responses.

Fourth, check the file before you upload it: every line must be valid JSON on its own, the system prompt must be identical on every row, and no user or system text may contain a reserved string. Fifth, train on that first batch and check your leaderboard score to establish a baseline. Sixth, iterate based on results by analyzing what types of questions your model handles well, identifying weaknesses, expanding successful patterns, and adding more examples in weak areas.

Common Data Quality Issues & Fixes
Problem: Generic, Wikipedia-Style Responses
Example: "The Bellagio is a luxury hotel and casino on the Las Vegas Strip. It features 3,950 rooms, a 156,000-square-foot casino, and was inspired by the Lake Como town of Bellagio in Italy."

Fix: Add personality, conversational tone, and practical advice.

Better: "The Bellagio is Vegas luxury at its finest! Don't miss the famous fountain show (best viewed from Paris Las Vegas's Eiffel Tower restaurant around 8 PM for dinner and a show). Inside tip: Check out the Conservatory early morning (before 9 AM) to avoid crowds and get perfect photos. If you're not staying here, at least grab a drink at Petrossian Bar to experience the elegant atmosphere without the high-roller price tag!"

Other common issues include inconsistent formatting (fix by standardizing all entries to match the proper JSON structure), overly long responses (keep most to 2-4 sentences), factual errors (verify all facts before including them), and lack of variety (use diverse prompt templates like "What's the best way to...", "Can you recommend...", "I'm interested in... what should I...", "How do I...", and "What's the difference between...").

How many examples
Use at least 100 examples. Anything smaller fails during training rather than producing a weak model. AWS recommends at least 200 per task you want the model to learn.

300 to 500 diverse examples is the range where most fine-tuning tasks land, and returns flatten past that unless the quality of what you are adding goes up too. Going much beyond that with similar-looking examples trades generalisation for memorisation, which shows up as a model that is strong on your own questions and weak on the evaluation set.

Grow the dataset deliberately rather than all at once, so you can tell which additions actually moved your score.

Adjusting Hyperparameters
Your data decides what the model learns. Hyperparameters decide how it learns. Same dataset, different settings, very different results.

Do this section after you have a baseline score on the board, and after you have improved your dataset. Tuning a weak dataset is wasted effort, so start with Dataset Curation.

Budget your time before you start
Every experiment is a full round trip: 20 to 25 minutes training, 10 to 15 minutes deployment, then up to 15 minutes for the leaderboard to score it. Call it an hour per attempt, and you can only run 2 training jobs at once.

So plan for three or four deliberate experiments, not twenty. Pick the changes below in order and stop when you run out of clock.

Where these settings live
Module 1 Step 12 walks through the customization screen and the hyperparameter fields. Two things worth remembering from it:

MLflow Resource is under Advanced options, it is required, and the job fails if the tracking server is still Creating.
Sequence length and Training type sit near the top of the form, separate from the numeric hyperparameter fields.
Watch what training actually did
The leaderboard tells you whether a model scored. It does not tell you why. That is what MLflow is for, and it is the field you already filled in.

Open your MLflow tracking server from SageMaker Studio and select the run matching your training job. Look at the training loss curve:

Falling steadily and still falling at the end. The model was still learning. More epochs or a higher learning rate should help.
Flat or barely moving. Nothing is being learned. Learning rate is too low, or warmup consumed the whole run. See the warmup note below.
Jumping around or spiking. Learning rate is too high. Cut it.
Falling fast then flattening early. It converged. Extra epochs from here mostly risk memorisation.
Check this before you change anything. Guessing from a leaderboard score alone wastes an hour per guess.

The fields you can change
Console field	Default	Console accepts	Worth knowing
Batch size	64	64, 128, 256, 512, 1024	64 is the minimum, and lower means more steps
Number of epochs	2	1 to 100	AWS recommends 5 or fewer, though higher runs fine
Learning rate	0.00001	0 to 1	keep it between 1e-6 and 1e-4
Minimum learning rate	0.000001	1e-7 to 1	must be lower than Learning rate
Warmup steps	10	0 to 100	see the warning below, 10 is too high for a small dataset
Alpha value	128	32, 64, 96, 128, 160, 192	those six values only
Learning rate ratio	16	1 to 70	optional, leave it alone until other levers are exhausted
Maximum Context Length	8192	1 to 131072	keep it on a 1024 multiple, and 8192 is already generous
The console's ranges are wider than AWS's recommendations. Epochs will accept 100 and the job will run. Nothing stops you, so the cost of an extreme value is wasted time and a memorised dataset rather than a rejected job.
Understand this before you tune anything
Supervised fine-tuning teaches the model behaviour: how to structure an answer, what tone to take, what format to follow, when to decline. AWS states it plainly:

SFT teaches the model new behaviors, response formats, and reasoning patterns. It does not teach the model new factual knowledge.

A dataset built to make the model recite facts will score poorly no matter how you tune it, and no setting on this page fixes that. What wins is consistent, well-structured, correctly-toned responses.

Watch out for warmup on a small dataset
Warmup is counted in optimiser steps, not examples, and a small dataset produces very few steps. Batch size cannot go below 64, so with 200 rows each epoch is 4 steps and two epochs is 8 steps total. The default warmup of 10 is longer than the entire run, and AWS warns about exactly this:

We recommend that you avoid a large warm up value when the training sample is small because the learning rate might never reach the set value during the training process.

AWS sizes warmup as dataset rows divided by 640 for Nova Micro, which for any dataset you will build here rounds down to the minimum. If your dataset is a few hundred rows, set Warmup steps to 1 or 2. Leaving it at 10 can mean your learning rate never arrives, which makes every other change on this page look like it did nothing.

A defensible first experiment
If you want one configuration to start from rather than a menu, use this on a dataset of a few hundred rows, then change one thing at a time from here.

Field	Value	Why
Warmup steps	1	so the learning rate actually reaches its target
Learning rate	0.00005 (5e-5)	AWS's recommended rate for LoRA, five times the console default
Minimum learning rate	0.000001 (1e-6)	default, and safely below the rate above
Number of epochs	3	small datasets need more passes, and 5 is AWS's recommended ceiling
Batch size	64	the minimum the console allows, so the most steps
Alpha value	128	keep the default until you have a reason
Maximum Context Length	8192	default, far more than a question and answer needs
What to change, in order
1. Your dataset. Not on this page, and still the largest lever by a wide margin. Go to Dataset Curation first.

2. Warmup steps. Cheap, and it gates whether anything else you change has an effect. See above.

3. Learning rate. The default 1e-5 is conservative. AWS recommends 5e-5 for LoRA. If MLflow shows loss jumping around, go down to 5e-6 instead. Stay within 1e-6 to 1e-4.

4. Number of epochs, which is your only real control over step count. Batch size cannot go below 64, so a small dataset produces very few optimiser steps per epoch: 52 rows is 1 step, 200 rows is 4, 500 rows is 8. Total steps is that number times your epochs, and a model cannot learn much in 3 steps.

Default is 2. AWS notes that smaller datasets need more epochs to converge and larger datasets need fewer, which is exactly this effect. On a couple of hundred rows, 3 to 5 is reasonable. On a very small set you may need more to get any steps at all, though you are then trading generalisation for memorisation. Growing the dataset is the better fix when you have the option.

5. Leave Batch size at 64. It is the lowest value the console offers, and lower means more updates from the same data. The other options go upward (128, 256, 512, 1024) and every one of them reduces your step count, which is the opposite of what a small dataset needs.

6. Alpha value. Default 128. Higher lets the adapter pull the model further from its base behaviour. If tuning barely registered, try 160 or 192. If output went incoherent, drop to 64. Use only the six allowed values.

7. Leave Maximum Context Length and Sequence length alone. 8192 tokens is far more than a question and answer pair needs. Raising either costs training time without improving anything, unless your records are genuinely long.

Minimum learning rate must stay below Learning rate. If you lower Learning rate to 1e-6, the default floor of 1e-6 is no longer below it and the job can be rejected.
Keep a log
Change one thing per run, and write down what it did. Otherwise an hour buys you nothing.

Track: dataset version and row count, then Epochs, Learning rate, Minimum learning rate, Batch size, Alpha value, Warmup steps, your leaderboard score, and one line on what you observed in the MLflow loss curve.

A worked sequence looks like: baseline on defaults, then dataset improvements holding everything else still, then warmup down to 1, then learning rate to 5e-5, then epochs to 3. Five runs, each isolating one change, each recorded.

Compare runs by their difference, not their absolute score. A change that moves you by less than the gap you have seen between two identical configurations is noise, so run your baseline twice early on to learn what that gap is for your setup.

When something goes wrong
The job fails as soon as I submit
Barely any change from the base model
Strong on my training questions, weak on new ones
Inconsistent or erratic answers
Score will not move no matter what I change
I cannot start another training job or deployment
